Introduction

Artifact 4 asked why models need to be explainable. This artifact asks the practitioner's follow-up question: which explanation technique, for which model, for which audience? The field's toolkit is large enough that listing techniques is no longer useful on its own — what a working engineer needs is a map. This page is that map. It places seven established techniques on three classification axes, traces each one to the real-world applications it serves, and ends with the trade-off every practitioner has to weigh: the tension between a model's accuracy and its interpretability, and why that tension is real but not absolute.

The Three Classification Axes

Every technique on this map is classified on the same three axes. Together they answer the three questions that determine whether a technique fits a situation: how much of the model it explains, what kind of model it works with, and when the explanation is produced.

Axis 1 — Scope: Global vs. Local

Global — Explains the model's behavior as a whole: which features matter overall, how the model responds to a feature across the dataset. Used for auditing, debugging, and understanding the model before deployment.

Local — Explains one prediction for one input: why this patient was flagged, why this loan was denied. Used when a specific decision must be justified to the person it affects.

Axis 2 — Model Access: Model-Specific vs. Model-Agnostic

Model-specific — Works only with a particular model family, because it reads something inside that model — gradients, attention weights, or the tree structure itself. Often faster and more faithful for the models it supports.

Model-agnostic — Works with any model, because it only needs to query the model: feed inputs in, observe outputs. The price of that generality is approximation — the explanation is built from the model's behavior, not its internals.

Axis 3 — Timing: Pre-Hoc vs. Post-Hoc

Pre-hoc (ante-hoc, intrinsic) — The model is interpretable by construction. There is no separate explanation step, so there is nothing for an explainer to get wrong — the explanation is the model. Decision trees and linear models are the classic examples.

Post-hoc — The explanation is produced after the model is trained, by a second method that inspects or probes it. This covers most of the modern toolkit — and it is why post-hoc explanations must be checked for faithfulness: they approximate the model, they are not the model.

Why Three Axes, Not One List

A flat list of techniques hides the decisions a practitioner actually makes. The same technique can be the right choice in one setting and the wrong one in another: SHAP answers a regulator's question about one denied loan and an auditor's question about the whole model, but in two different forms. Classifying on three axes makes those distinctions visible — and makes it obvious when a technique cannot do what is being asked of it (a local method cannot audit a whole model; a model-specific method cannot explain a model it was not built for).

The Techniques, One by One

Decision Trees

GlobalModel-specificPre-hoc

What — A tree is interpretable by construction: every prediction follows a path of readable if–then rules from root to leaf, and the whole model fits on one page for a small tree. There is no separate explainer, so the explanation cannot drift from the model. Used for — Clinical decision rules, credit policy, and anywhere a human must be able to read the entire decision logic — and as the baseline every post-hoc method is compared against.

Partial Dependence Plots (PDP)

GlobalModel-agnosticPost-hoc

What — Introduced by Friedman (2001), a PDP shows how the model's average prediction changes as one feature varies, holding the others at their observed values. It answers "what does the model think this feature does?" across the whole dataset. Used for — Auditing a model for sensible behavior — for example, checking that a pricing model's response to mileage is monotone — and for spotting reliance on a feature that should not matter. Caveat — It can mislead when features are strongly correlated, because it averages over feature combinations that never occur in reality.

SHAP

Local+ GlobalModel-agnosticPost-hoc

What — SHAP (SHapley Additive exPlanations, Lundberg & Lee, 2017) assigns each feature a value for one prediction: how much it pushed the result up or down, grounded in Shapley values from cooperative game theory. The contributions add up to the prediction, which makes the explanation consistent and checkable. Averaging the values across the dataset produces a global importance ranking. Used for — Credit scoring and clinical risk models, where "which feature mattered, and how much" is the question a regulator or a doctor asks about one decision — and about the model as a whole.

LIME

LocalModel-agnosticPost-hoc

What — LIME (Local Interpretable Model-agnostic Explanations, Ribeiro et al., 2016) explains one prediction at a time: it probes the model with slightly changed versions of the input, then fits a simple, readable model to that local neighborhood. It works with any classifier, which is why it spread so fast. Used for — Explaining individual decisions in text, image, and tabular models — for example, highlighting the words that drove one document classification. Caveat — Explanations can shift between runs, and the local model is only faithful in a small neighborhood around the input.

Counterfactual Explanations

LocalModel-agnosticPost-hoc

What — Proposed by Wachter, Mittelstadt, & Russell (2018), a counterfactual explanation states the smallest change to an input that would have produced a different decision: "your loan would have been approved if your income had been $5,000 higher." It needs only to query the model, so it works with any classifier. Used for — Adverse-action notices in lending and hiring, where the person affected needs a concrete, actionable reason — not a feature weight, but a path to a different outcome.

Saliency Maps

LocalModel-specificPost-hoc

What — Introduced for convolutional networks by Simonyan, Vedaldi, & Zisserman (2014), a saliency map computes how strongly each pixel influences the model's output and renders the result as a heatmap over the image. It needs the model's gradients, so it only works with differentiable models. Used for — Medical imaging (which region of the scan drove the diagnosis) and autonomous driving (what the system saw before a maneuver), where the evidence is spatial and must be seen, not listed.

Attention Visualization

LocalModel-specificPost-hoc

What — For transformer models (Vaswani et al., 2017), attention maps show which input tokens the model weighted most when producing an output. The weights are part of the model itself, but reading them as an explanation happens after the fact, which is why attention visualization sits on the post-hoc side of the map. Used for — Debugging language-model behavior and translation, where seeing which words the model attended to helps explain an odd output. Caveat — Attention shows focus, not reasoning: a model can attend to a word without that word causing its answer, so an attention map is a clue, not proof.

What the Map Leaves Out — Deliberately

Not every explainability idea fits on this map, and that is a design choice, not an oversight. Chain-of-thought prompting and sparse autoencoders (covered in Artifact 4) are explanation-adjacent — one generates stated reasoning, the other decomposes a model's internals — but neither is a technique for explaining a trained classifier's decision, so neither belongs in this classification. A taxonomy earns its keep by what it excludes as much as by what it includes.

How to Choose: Four Questions in Order

1. Who is it for?

A clinician, a loan applicant, a regulator, or an engineer debugging? The audience sets the language the explanation must speak.
→

2. Global or local?

The whole model's behavior, or why this one prediction happened? This picks the side of the map.
→

3. Can you change the model?

If yes, consider an interpretable model (pre-hoc). If the model is fixed, add a post-hoc explainer.
→

4. Match the tool

Tabular + local → SHAP / LIME. Image + local → saliency. "What would change it?" → counterfactuals. Audit → PDP / SHAP summary. Transformer → attention.

The order matters. Starting from the technique — "we use SHAP" — and working backwards is how teams end up explaining the wrong thing: a local explanation handed to an auditor who needed a global one, or a post-hoc approximation where a readable model would have done. The question comes first; the technique follows.

The Accuracy–Interpretability Trade-Off

The chart below shows the pattern every practitioner meets: as models get more flexible — and usually more accurate on complex data — they get harder to explain. The dashed curve is the typical frontier: the accuracy you can expect at each level of interpretability.

The honest caveat. The frontier above is a tendency, not an iron law. Rudin (2019) argues that in many high-stakes domains — medical risk scoring is her central example — a well-designed interpretable model can match a black box, because the accuracy gap often comes from a poorly tuned simple model being compared against a carefully tuned complex one, not from any law of nature. The trade-off should be measured in each domain, not assumed. My own Workshop Four experiment is a case where the trade-off was real: the decision tree's recall was 0.76 against the neural network's 0.90 on the same held-out test set, so the readable model genuinely cost accuracy there — but that result belongs to that dataset, and I would not carry it into the next domain without measuring again.

That is the practical meaning of the chart: interpretability is a design choice with a price that varies by problem. Where the price is zero, take the interpretable model — there is nothing to trade away. Where the price is real, as in my 4.2 experiment, the honest answer is a post-hoc explainer on the accurate model, with the caveat that the explanation is an approximation and must be checked. Either way, the decision is made with numbers, not with a slogan.

Summary

Explainability techniques are not interchangeable, and a list of them is not a toolkit. The three axes — scope, model access, timing — turn the list into a map: they show which techniques can answer which questions, which ones can be combined (SHAP's local values aggregating into a global view), and which ones cannot do what is being asked of them. The applications table shows the map in use: the question determines the scope, the model determines the access, and the two together pick the technique. And the trade-off chart closes the argument honestly: accuracy and interpretability usually pull in opposite directions, but the pull is a tendency to measure, not a law to accept — and the measurement, as my 4.2 experiment showed, is what makes the choice defensible.

Process

I built this artifact by first fixing the classification scheme, then placing the techniques in it — not the other way around. The three axes come from the standard taxonomy in the interpretability literature (Molnar, 2022): scope, model access, and timing are the dimensions the field itself uses to sort methods. I chose scope as the map's primary split because it matches the first question a practitioner asks — the whole model or this one prediction — and carried the other two axes as labels inside each node, so the map stays readable while the full classification is still visible. The hard placements were the interesting ones: SHAP spans both scopes (local values, global summary), so it appears twice rather than being forced into one box; attention visualization is model-specific and post-hoc in use, even though the weights it reads are part of the model; and decision trees are the only pre-hoc technique in the set, which is itself a finding — nearly the entire modern toolkit is post-hoc, which is why faithfulness is the field's central worry. I verified each technique's description and citation against its source paper before writing, kept the trade-off chart's positions explicitly illustrative, and used my own 4.2 experiment — not a textbook number — as the one measured trade-off on the page. The classification process and learning reflection are in the accompanying document submitted with this artifact.

Value Proposition — Unique Value and Relevance

Artifact 4 showed I can explain why a model must be explainable. This artifact shows I can do something about it: given a model, an audience, and a question, I can pick the technique that fits — and say why the others do not. That is the skill a deployment actually needs: not knowing that SHAP exists, but knowing when SHAP is the answer, when a counterfactual is, and when the right move is a readable model in the first place. Combined with the validation discipline from Artifact 4, it is the complete picture: measure honestly, then explain with the right tool.
